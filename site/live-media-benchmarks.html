A smaller origin for the same viewer workload

Sapflow takes H.264 and AAC over SRT or RTMP, packages Low-Latency HLS and records fragmented MP4. Keeping that job small gives an operator a concrete reason to evaluate it: the 16-worker own HTTP loop used 79% less CPU and 90% less process RSS than MediaMTX in this test.

The 79% CPU and 90% RSS comparison uses the 16-worker own loop; Hyper remains the default and used 64% less CPU than MediaMTX here. One own-loop worker reduced CPU further, with a higher playlist p99 and median part fan-out delay than sixteen.

The HTTP implementation is a useful tuning target in its own right. Against Sapflow on Hyper, the 16-worker own loop cut measured CPU by 43% and peak RSS by 89%. The ingest and packaging paths were shared between those configurations.

Test conditions, source versions and raw results

Generated 720p30 H.264/AAC over RTMP, native ARM64 release binaries, loopback HTTP/1.1, recording off and no TLS. Server, encoder and load generator shared the M4 Max with existing host workloads. Each trial had warm-up, a ten-second viewer ramp and a sixty-second full-load target.

The measured Sapflow development snapshot is 2d20835ef246740ab42ca810df7c51fd43bf9ff6, ahead of the published 0.1.0 crates. These figures don't requalify another source revision. The load generator includes ramp traffic in its counters and percentiles. It fetches overlapping parts and segments and doesn't fetch MediaMTX's separate audio rendition; its byte count isn't unique-media throughput. Peak RSS excludes kernel memory.

The broadcast path

  1. Encode

    A native app or an existing encoder produces compressed H.264 video and AAC audio.

  2. Publish

    SRT carries media over UDP with recovery. RTMP provides a publishing path for existing tools.

  3. Package

    Sapflow writes HLS parts, segments and playlists, with optional MP4 recording.

  4. Watch

    A player fetches HLS over HTTPS. A reverse proxy supplies TLS and HTTP/2.

The native adapters own the camera, microphone, hardware codecs and sockets. The shared Rust libraries process compressed media. Sapflow doesn't transcode a stream or create an adaptive bitrate ladder.

Why separate libraries?

An application may need a publisher without a server, or a packager without a network runtime. Separating protocol state from sockets lets the same code run under a server event loop or a native platform adapter.

The libraries share a repository. Each has a specific responsibility.

RelaySwarm shares media. Spry connects peers.

RelaySwarm lets viewers exchange verified HLS media over WebRTC data channels, using application-selected Nostr relays for rendezvous. RelaySwarmKit provides the Swift implementation. The HTTP origin remains the fallback when peers can't provide media in time.

Some peers can't connect directly through their networks. Spry TURN is our small Rust STUN/TURN server for that relay role: UDP and TCP client connections, optional TLS, coturn-compatible shared-secret credentials and bounded resources. It can run separately from the media server.

RelaySwarm accepts ICE server configuration, where an operator can supply Spry or coturn. The relay still needs reachable addresses, credentials and bandwidth. Spry is optional for peer connectivity; ordinary Sapflow SRT/RTMP ingest and HLS playback don't require it.

More UDP and TLS delivery in the measured workloads

The published Spry 0.2.1 M4 Max binaries delivered 16–22% more UDP packets per second and 27–35% more TLS packets per second than the tested coturn configuration. TCP ranged from 1.2% behind to 8.5% ahead. The complete M4 matrix contains 108 runs and 53,075,648 checked forwarded packets, with no observed payload loss, reordering or corruption.

Platform choice matters. Spry was slower in five of six UDP workloads on the constrained Linux ARM64 VM. At 128 allocations and 1,200-byte payloads it was 15.4% behind coturn over UDP, 46.8% ahead over TCP and 30.2% ahead over TLS. These VM results need a separate trial on an operator's Linux host.

RelaySwarm's desktop HLS composition remains under qualification. An earlier fixture shared one TURN credential across viewers and hit Spry's allocation quota. A corrected Spry 0.2.1 run with separate viewer credentials passed UDP at 81% in-time delivery. TCP and TLS carried verified media without ICE errors but reached 27% and 37.8%, below the unchanged 50% gate. TLS also had no active selected path at the final sample and used an explicit test-certificate bypass. The remaining timing failure has not been isolated to either implementation. HTTP playback and tampering rejection passed. The composition results and fixture correction are pinned to the public main-branch update checked on 24 October 2026 and remain separate from the standalone relay benchmark. The scalar receipt retains the failed gates. Internet NAT and physical-phone acceptance remain open.

The actual KithMoot web client, through ordinary TURN settings

Spry 0.2.1 also passed a separate local browser qualification using the actual KithMoot web application. Two clients exchanged and decoded generated audio/video through forced UDP, TCP and TLS relay paths, with operator-generated short-lived credentials entered through the real Connections settings. No HTTP credential issuer or publisher-operated default was added, and the client made no /turn request. This qualifies the identified web source and executable on one machine; TLS used an explicit test-certificate bypass. Cross-network reachability, public certificate validation and physical GrapheneOS acceptance remain separate gates. Read the accepted path and limits and versioned browser receipt.

What changed, platform limits and all relay samples

Spry reserves packet headroom to avoid a second media-payload copy, uses bounded readiness slots and connected client-facing UDP sockets for authenticated, concrete-IPv4 allocations. Wildcard/IPv6 listeners use the portable path. Version 0.2.1 also caches writable-interest state: the event loop registers write readiness when output blocks and removes it after draining. A separate controlled before/after M4 experiment measured 5.8% higher Spry TCP delivery and 4.4% higher TLS delivery.

The primary M4 matrix covers 1, 16 and 128 allocations, 160- and 1,200-byte payloads and UDP/TCP/TLS, with an eight-packet window per load worker. It uses generic ARM64 release builds without PGO and coturn 4.18.0 with one relay event loop. Each throughput phase completes at least 200,000 round trips over at least two seconds. Existing workloads remained running. These closed-loop medians establish neither maximum WAN capacity nor statistical significance.

Process memory and kernel memory have separate budgets. The connected-UDP path holds an extra client-facing socket per allocation. TCP buffering can cost more process memory than coturn: the controlled 128-allocation experiment measured 12.21 MB versus 11.70 MB RSS over TCP. Linux socket counters include nonzero drops despite successful payload checks, so the results do not establish zero kernel drops.

Add storage and transfer when the application needs them

Move a recording

ForgeSworn Link provides a separate transfer protocol. It isn't an ingest protocol or a required Sapflow dependency. Broadcast-time recording transfer needs its own integration and contention measurements.

Store and recover files

Shelter Kit provides content-addressed storage and repair interfaces. Foregather can supply pairing or invitation flows. Neither belongs in a media callback or is required for basic HLS delivery.

What the measurements establish

The origin and relay comparisons establish resource savings in their documented workloads. They provide a reason to trial Sapflow and Spry on an operator's traffic and measure the resulting headroom.

Those results don't establish Linux capacity, internet latency, phone battery life or sustained hardware-codec performance. Server, load generator and encoder sharing a Mac also compete for resources. Read the conditions alongside the numbers before using them to size a deployment.

The native performance contract sets out copying, queueing and physical-device gates. New measurements belong with their exact source and binary versions.
